# EX003：端侧 LLM 能力边界与项目目标可达性

> 问题：**利用端侧 LLM 的能力，是否能实现 Step-RL 的整个项目目标？**
>
> 结论：**不能只靠端侧 LLM。** 端侧 LLM 能完成本地/受控站点的语义决策与兜底，
> 但真实多站目标还依赖适配器、登录/风控合规、权威验证器、账号与真实证据。
> 本报告只引用真实执行 JSON，不使用 mock。

## 1. 已有真实证据

| 能力/条件 | 真实结果 | 来源 |
|-----------|----------|------|
| 本地纯 LLM 扁平执行（9 任务） | **88.9%（8/9）**，323.18s | `outputs/ex001/e2_flat.json` |
| 本地层级 + 语义（9 任务） | **100%（9/9）** | `outputs/ex001/e2_flat.json` / `outputs/ar004/eval/semantic_stable.json` |

## 2. 端侧 LLM 能做到什么

1. **本地/受控页面的语义决策**：8/9 扁平；层级+语义 9/9；
2. **兜底与修复**：技能失败后 LLM 可执行兜底轨迹，再由验证器确认；
3. **语言/规划**：自然语言约束、候选动作生成、错误修复；
4. **低显存**：1.28GB，可在端侧 16GB 卡上运行。

## 3. 端侧 LLM 不能解决什么

| 缺口 | 为什么 LLM 不能解决 | 真实证据 |
|------|----------------------|----------|
| 登录/验证码/风控 | 需要人工/授权，绕过不合规 | JD 搜索页登录跳转；淘宝空标题/反爬 |
| 页面无商品链接 | 没有可执行元素，模型只能猜 | JD `item_links=0`；加购控件不存在 |
| 成功判定 | 模型文本不能替代服务端验证 | 移除验证器观测 100%→33.3% |
| 账号/订单/支付 | 需要授权、限额、人工确认 | AR029 设计明确 dry-run；无真实订单 |
| 成本/延迟 | 每步 8.31s，长链路不可接受 | EX001 E8 |
| 多站 DOM/条款 | 需要站点 adapter/合规评审 | Taobao/Amazon 差异；AR030 只读 |

## 4. 项目目标可达性判断

| 目标 | 只靠端侧 LLM | 当前混合架构 |
|------|--------------|--------------|
| 本地搜索/加购/结算 | 部分（8/9，长链路退化） | **30/30、0 LLM** |
| 本地故障恢复/事务 | 不可靠（无补偿/验证） | 0/2→2/2、0/3→3/3 |
| 真实 JD 只读搜索 | 不能解决无商品链接 | 搜索页可开，但结果为空 |
| 真实 JD 加购/结算 | 不能解决登录/控件缺失 | 需登录接管与 DOM 适配 |
| 淘宝/Amazon 多站 | 不能绕过反爬/账号 | 只读部分验证 |
| 可审计成功率/CI | 不能替代真实验证器 | 需要 n≥30 与账号 |

**判断：端侧 LLM 是“决策/兜底层”，不是“项目全部”。**

## 5. 推荐的混合闭环

1. **确定性层**：adapter/selector/verifier/cart/transaction；不依赖 LLM；
2. **端侧 LLM 层**：仅用于未覆盖能力、语义歧义、失败修复；
3. **人工层**：登录/验证码/支付/高风险确认；
4. **证据层**：服务端/订单页权威状态，LLM 文本不授予成功；
5. **评测层**：技能 0-LLM 路径与 LLM 兜底路径分开报告，避免用 LLM 成功率掩盖 adapter 缺口。

## 6. 回答

- **能实现“本地/受控电商闭环”**：是，已有 30/30、0 LLM 与真实订单/事务证据；
- **能实现“真实主流电商全链路”**：**仅靠端侧 LLM 不能**；必须补齐 adapter、登录合规、
  权威验证器、账号与真实样本；
- **正确路线**：端侧 LLM + 确定性 adapter/verifier + 人工接管，而不是把全部任务交给模型。

## 1. 背景与目标

用户可能一次提出多个独立订单：“先买 A 并结算，再买 B 并结算”。现有系统会把 A、B 聚合成一笔订单，无法满足序列语义。

AR016 增加：

- 服务端订单历史（多订单）；
- TaskSpec 订单序列；
- 运行时按序列逐单执行（技能加购 + 结算，订单后清空购物车）；
- `orders_sequence_placed` 序列验证器；
- 基线 LLM vs 序列运行时对照。

目标：多订单 2/2，基线 0/2；否则回退。

## 2. 范围

**In：**
- 服务端 `orders` 历史与快照；
- TaskSpec `order_sequence`；
- 序列验证器；
- 技能层级 `reset=False` 的连续执行；
- 2 个多订单任务评测；
- 单测、报告、README、复现文档。

**Out：**
- 任意多轮对话；
- 新模型训练；
- 公网。

## 3. 功能需求

### FR1 订单历史

- `/place-order` 追加到 `orders`，`order` 保留最后一单兼容；
- `/api/state` 返回 `orders`。

### FR2 订单序列

- TaskSpec `order_sequence: List[Dict[pid,int]]`；
- 谓词 `orders_sequence_placed`：每个目标订单在历史中存在且数量满足。

### FR3 序列执行

- 第 1 单 reset；后续不 reset，购物车在订单后已清空；
- 每单：技能加购 + 结算；
- 最终由序列验证器判定。

### FR4 评测

| 任务 | 订单序列 |
|------|----------|
| M1 | p3×1；p2×2 |
| M2 | p4×2；p1×1 |

- baseline：LLM 层级 + 合并采购（一笔订单）；
- runtime：序列技能；
- 成功按序列验证；记录订单历史。

## 4. 非功能

| 类型 | 要求 |
|------|------|
| 训练成本 | 0 |
| 技能耗时 | <8s/任务 |
| 可复现 | 固定 seed、JSON |
| 安全 | 真实 DOM/动作白名单 |

## 5. 假设

- 订单后购物车清空；
- 会话可连续下单；
- LLM 倾向聚合订单。
